# dex-arbitr 项目说明

版本：与仓库代码同步（2026-08-23）  
阶段：**P1 监控**。默认 `monitor_only: true`，识别机会、规划双腿，**不下单**。签名 `place()` / `cancel()` 尚未接线。

安装与启动见 [部署文档.md](部署文档.md)。与参考 Python 项目的差异见 [套利流程对比.md](套利流程对比.md)。早期规划稿见 [开发设计文档.md](开发设计文档.md)（部分目录与公式已过时，**以本文和代码为准**）。

---

## 1. 做什么

在 **Lighter 主网**（USDC）和 **Lighter Robinhood**（USDG）的永续订单簿之间做价差对冲：一侧开多、一侧开空，锁住可成交价差。稳定币按 **1:1**（`BTC-USDC` ≡ `BTC-USDG`）。热路径不搬家、不兑币、不跨链。

两边是同一 Lighter 协议的两个实例（不同 URL、`chain_id`、计价币），共用一个适配器、两份 venue 配置。

当前白名单只有 **BTC**。决策用分段网格（SEG-GRID），`max_segments: 1`，实际只开一格。

| 阶段 | 状态 | 内容 |
|------|------|------|
| P1 | **进行中** | 发现、匹配、净价差、格子决策、先挂后吃规划、控制台面板、SQLite 中位数 |
| P2 | 未做 | 同一进程提供 HTTP/WS 监控页 |
| P3 | 未做 | 更多 DEX、资金费率独立路径 |

## 2. 架构与目录

单 crate、单进程。页面不直连交易所。新交易所只加适配器 + 配置，Controller 流程不变。

```
启动 main
  → 读 config/default.yaml + venues
  → Controller：拉市场、匹配、订 WS
  → 盘口事件 → 计价 / 决策 / 规划
  → 面板刷新 + SQLite 采样
  → monitor_only：只打日志，不发单
```

## 3. 端到端流程

```
启动
  → 加载两所配置（密钥可空）
  → REST 拉永续市场，白名单过滤
  → 标准化 pair_id，两侧都有的才进监控
  → 订阅两侧 orderbook（事件驱动，无 100ms 空转）

每次一侧盘口更新
  → 另一侧还没有                 → skip wait
  → 盘口过期 / 交叉 / 深度不够    → skip stale | invalid_bbo | thin_book
  → 脱锚（P1 现传 1.0，不会触发） → skip depeg
  → 两个方向算价差，取净边更好的
       走深失败或滑点超上限      → skip no_spread
  → 每 5s 把 raw 写入 SQLite
  → nat = 该方向 24h raw 中位数（满 10 点才有）
  → res = net − max(nat, 0)
       样本不够且空仓             → res 强制 0，不开仓
  → 格子：res ≥ T1 且站稳 1s     → intent=open
       有仓且 res < T0 或反向    → intent=close（P1 内存仓几乎为空）
       否则                      → hold
  → 已有挂单等待                 → 价差还在且未超时则 limit
       价差没了 / 超时           → 记 cancel；若已成交则 late_hedge
  → 规划：taker 更高的所先挂限价，另一所后市价
  → monitor_only                 → skip_send，不调用交易所
  → 关 monitor_only 也只 warn    → 签名未接线
```

`skip_*` 是过滤，不是「错过了开仓」。开仓只看连续的 `intent=open`。

## 4. 价差公式

全部百分比。可成交价差，**不用中间价**。

```
raw  = (卖所 Bid1 − 买所 Ask1) / 买所 Ask1 × 100

limit_then_market（当前默认）:
  fee  = 先挂所 maker + 后吃所 taker
  slip = 只走市价那一腿的订单簿（卖一不够吃卖二、卖三）
  当前费率：RH 先挂 → 0.012 + 0.005 = 0.017%

market_taker:
  fee  = 两边 taker（0.005 + 0.035 = 0.040%）
  slip = 买腿走 ask + 卖腿走 bid

net  = raw − fee − slip
nat  = 该 pair + 该买卖方向、24h 内 raw 的中位数
res  = net − max(nat, 0)
```

滑点：

```
买入滑点 = (吃 ask 的 VWAP − Ask1) / Ask1 × 100
卖出滑点 = (Bid1 − 吃 bid 的 VWAP) / Bid1 × 100
```

`cost.default_slip_pct: 0.01` 是 **上限**：走深滑点超过 0.01% 则丢掉该方向（面板 `no_spread`）。不是固定再扣 0.01%。`0` 表示不封顶。深度累计不够 `base_qty` 也算不出均价，同样丢掉。

谁先挂：

1. taker 更高的所先挂限价  
2. taker 相同 → maker 更低的所先挂  
3. maker 也相同 → 两边都吃（fee = 两边 taker，slip 走两腿）

当前：RH taker 0.035% > 主网 0.005%，所以 **RH 先挂、主网后吃**。

开仓门槛：**`res ≥ 0.03%`（T1）且持续 1 秒**，不是看 `raw`。历史样本里 `res` 远小于 T1 时，一直 `hold` 是符合规则的。

## 5. 格子

```
T1 = initial_spread_threshold          # 0.03%
T0 = T1 × 0.4                          # 0.012%
Tn = T1 + (n − 1) × grid_step          # max_segments=1 时用不到
```

空仓：`res ≥ T1` 且持续 `persistence_ms` → `Open { qty: base_qty, buy, sell, grid: 1 }`  
有仓：`res < T0` 或买卖方向反了 → 持续同样时间后 `Close`  
同一交易所对禁止反向双开；反向信号走平仓。

`max_segments` 与 `grid_step` 已写入配置，决策里目前按 **一格** 处理。FIFO 多格未接。`positions` 只在内存，P1 监控路径 **不会写入**，因此运行时几乎走不到 Close。

## 6. 下单规划（未发到交易所）

`limit_then_market` 计划：

1. 第一腿：taker 更高的所，限价（maker）  
2. 第一腿成交后：另一所市价  
3. 挂着期间 `res` 掉到 T1 以下，或超过 `limit_timeout_ms`（2000ms）→ 撤未成交单  
4. 已经成交（含撤单前成交）→ 另一边仍市价对冲（`late_hedge`），避免单边  

`order.style` 还可切 `market_taker`（双市价）或 `limit_maker`（双限价）。关 `monitor_only` 目前也只打 warn，不会真下单。

## 7. 配置字段

### 7.1 `config/default.yaml`

| 字段 | 当前值 | 含义 |
|------|--------|------|
| `system.monitor_only` | `true` | `true` 只监控。关了也不会发单，直到签名接线 |
| `system.data_freshness_ms` | `3000` | 一侧盘口超过该毫秒未更新 → `stale` |
| `system.stable_depeg_bps` | `20` | USDC/USDG 偏离超过 20bp 停开。P1 未接实时比价，现传入 `1` |
| `venues` | `[lighter, lighter_rh]` | 加载顺序：0=主网，1=RH |
| `pairs.whitelist` | `[BTC]` | 空数组表示不过滤。只匹配永续 |
| `grid.initial_spread_threshold` | `0.03` | T1，单位 **百分比**（`0.03` = 0.03%） |
| `grid.grid_step` | `0.03` | 多格间隔；一格时不影响决策 |
| `grid.max_segments` | `1` | 最大格数。决策实际按 1 格 |
| `grid.persistence_ms` | `1000` | 开/平信号需连续站稳的时间 |
| `grid.base_qty.BTC` | `0.001` | 一格数量；也是走深数量 |
| `order.style` | `limit_then_market` | 见第 6 节 |
| `order.limit_timeout_ms` | `2000` | 第一腿限价最长等待 |
| `cost.default_slip_pct` | `0.01` | 走深滑点上限（%）。`0` = 不封顶 |
| `history.enabled` | `true` | 是否记 SQLite |
| `history.db_path` | `data/spreads.sqlite` | 相对工作目录 |
| `history.sample_interval_secs` | `5` | 同一方向最少间隔 |
| `history.window_hours` | `24` | 中位数窗口 |
| `history.min_points` | `10` | 少于此数：只记账，空仓 `res=0` |
| `history.max_age_secs` | `200` | 中位数内存缓存寿命 |
| `risk.min_book_qty.BTC` | `0.001` | 两侧买卖盘累计深度下限（与 `base_qty` 取大） |

百分比在 yaml 里写成 `"0.03"` 表示 **0.03%**，不是 3%。

### 7.2 `config/venues/*.yaml`

| 字段 | 主网 | RH | 含义 |
|------|------|----|------|
| `id` | `lighter` | `lighter_rh` | 必须与 `venues` 列表一致 |
| `rest` / `ws` | 主网 URL | `api.rh.lighter.xyz` | REST 拉市场，WS 订簿 |
| `chain_id` | `304` | `466324` | 签名用；监控可不填对 |
| `quote` | `USDC` | `USDG` | 匹配时都归一成 USD |
| `fees.maker` / `fees.taker` | `0.005` / `0.005` | `0.012` / `0.035` | 单位 %。按账户档位改 |
| `account_index` | 账户号 | **独立账户** | 不要复用主网密钥 |
| `api_key_index` | 一般 `0` | 一般 `0` | |
| `api_key_private_key` | 私钥 | 私钥 | 空或 `0x` = 未加载，监控仍可跑 |

`market_index` **不写在配置里**，启动时按交易对从 `orderBooks` 拉取。

## 8. 控制台字段

前台交互终端会原地刷新。Windows 不要用 `cargo run`（Cargo 管道会破坏回退光标），直接跑编译好的 exe。

统计拆成两短行（`decide` / `filter`），价差也拆成两行，避免一行太长在窄终端折行后留下多份 `intent`。

### 8.1 统计行

```
decide  hold=2709  open=0  close=0  skip_send=0
filter  stale=4  thin=0  spread=0  cancel_gone=0  cancel_to=0  late_hedge=0
```

| 字段 | 含义 |
|------|------|
| `hold` | 有完整价差，但不够开/平 |
| `open` / `close` | **决策层**：格子本轮给出开仓 / 平仓。监控模式也会加 |
| `skip_send` | **执行层**：已经做出计划，但 `monitor_only` 没发到交易所 |
| `stale` | 一侧盘口超过 3s |
| `thin` | 累计深度 < `min_book_qty` 与 `base_qty` 的较大者 |
| `spread` | 走深失败或滑点超上限（`no_spread`） |
| `cancel_gone` | 挂单未成且价差不够，应撤 |
| `cancel_to` | 挂单超时应撤 |
| `late_hedge` | 第一腿已成交，另一边仍应对冲 |

`open`/`close`/`hold` 和 `skip_send` **不是互斥分桶**。同一轮：格子说开仓 → `open+1`，接着因监控不下单 → `skip_send+1`。所以监控时常见 `open` 与 `skip_send` 一起涨，价差行仍显示 `intent=open`，表示「识别到了，故意没发」。

`wait`、`invalid_bbo`、`depeg` 会计入 skip，不一定单独出现在这一行。

### 8.2 盘口行

`venue` `pair` `bid` `ask` `bq` `aq`（后两个是买一/卖一数量）  
`pair` 是标准化 id（`BTC-USD-PERP`），不是所方原始名。

### 8.3 价差行

第一行：`pair` `buy` `sell` `intent` `pts`  
第二行：`raw` `slip` `net` `nat` `res`

| 字段 | 含义 |
|------|------|
| `pair` | `BTC-USD-PERP` |
| `buy` / `sell` | 本轮买所 / 卖所 |
| `raw` | 可成交毛价差 % |
| `slip` | 市价腿走深滑点 % |
| `net` | `raw − fee − slip`（**未减** nat） |
| `nat` | 24h raw 中位数；样本不够显示 `--` |
| `res` | 决策用净边。样本不够且空仓为 `+0` |
| `pts` | 有 nat 时是窗口样本数；否则 `已有/10`。**不是点位** |
| `intent` | `hold` / `open` / `close` / `limit` / `skip` |

`intent=skip` 时看 `note`：`stale`、`thin_book`、`invalid_bbo`、`no_spread`、`depeg`、`wait`。

## 9. 核心类型

```
VenueId          "lighter" | "lighter_rh"
VenueMarket      venue, raw_symbol, pair_id, base, market_index, qty_precision, min_qty
Pair             pair_id（如 BTC-USD-PERP）+ 两腿 VenueMarket
Bbo              bid/ask/qty + 多档 bids/asks + ts
NetSpread        buy, sell, raw_pct, fee_pct, slip_pct, net_pct
Position         pair_id, buy, sell, qty（内存；P1 监控不写）
Intent           Open { qty, buy, sell, grid } | Close { qty, grid } | Hold
HedgePlan        数量、买卖所、first/second 腿（style + is_buy）
LimitWatch       StillWait | CancelSpreadGone | CancelTimeout | FilledHedgeNow
```

匹配规则：只取永续；`USDC` / `USDG` / `USDT` / `USD` 都视为 USD；`pair_id = {BASE}-USD-PERP`；两侧同一 `pair_id` 才进监控。下单仍用所方 `raw_symbol` 和 `market_index`。

## 10. SQLite

表 `spread_samples`：`ts, pair_id, buy, sell, raw_pct, net_pct`。  
中位数只对 **raw** 计算，按 `pair_id + buy + sell` 分方向。清空：停进程后删 `data/spreads.sqlite`，`nat` 会重新攒满 10 点。

## 12. 怎么判断「识别对了」

盯盘时记同一时刻的 `raw` / `slip` / `net` / `nat` / `res` / `pts` / `intent`：

1. 有没有连续 `intent=open`（不是一跳）  
2. `res` 是否真的 ≥ `0.03`  
3. `skip_stale` / `skip_spread` 不要当成错过的开仓  
4. `pts` 未满 10 时 `res` 应为 0  

确认稳定后再考虑接线签名。在此之前不要当实盘。
